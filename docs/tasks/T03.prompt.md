## 要做的事

### 1. 数值原语 `src/core/num.ts`

- float32：一律经过 `Math.fround`。
- 整数：按 ARM 的「float 转 int」规则向零截断；int32 / uint32 的溢出和乘法用 `Math.imul` 或 `>>> 0`。
- 每个原语都要有单元测试，覆盖负数、边界和溢出。

### 2. RNG `src/core/rng.ts`

- 严格照 `01-board.md`「随机数」一节实现：6 路 uint32 状态、乘数 16807、`RandUnitF` 的位构造、`Rand`、`RandI`、`SetRandSeed`（包括 6 号「全部」哨兵）、`FlushRandSeeds`、`GetRandSeed`。
- 每次调用都必须显式传入 `RandType`。另外提供调用记录钩子，供测试断言「第几次调用、哪一路、范围是多少」。
- 测试要求：
  - 用公式在测试里独立算出前若干个值，再和实现逐个对拍，包括零种子保持为零；
  - 针对位构造，测试 `RandUnitF` 等于 `(seed >>> 10) / 4194304`；
  - 测 `RandI` 的端点和 a > b 的情况。

### 3. 数据加载层 `src/core/data.ts`

- 读取 `data/enums.json`、`items.json`、`classes.json`，并导出带类型的常量或查表函数。
- 枚举名到数值的映射以 `enums.json` 为准。数值一律来自数据表，不在代码里硬编码；每处用到数据的地方注释出数据来源。

### 4. 状态模型 `src/core/state.ts`

- 按 T02 报告第 1 条建议，把 `RunState`（局内）和 `ProfileState`（长期）分开，字段覆盖 00–06 规格中出现的局内状态，包括：
  - 6×6 格子；
  - 基础属性与装备派生属性分开保存；
  - 五件装备、四个技能；
  - 三条资源条的余数、累计值和进位；
  - 玩家中毒、晋升计时；
  - 当前和下一回合的技能标志；
  - 链节点与箭头忽略格；
  - 待结算队列、菜单队列、回合阶段；
  - 6 路 RNG 状态。
- 后续卡要用到的字段可以先定义好、给初始值，但对应逻辑留空。
- 字段名用可读的英文。注释里写出对应的原版偏移，例如 `// Game+0xc23c`，方便以后对照。

### 5. 入口与阶段 `src/core/engine.ts`

- `step(state, action) → { state, events }`：在边界做一次深复制，内部可以用可变写法。
- `Action` 和 `GameEvent` 写成判别联合类型。本卡只需实现 `NewGame`（参数为 seed、职业、难度、模式），其余 action 返回明确的「未实现」错误，不要静默忽略。
- 未决规格做成开关：建立 `src/core/options.ts`，把 B1、B2、C2、C3、C4、I1 等做成具名选项，给出默认值，并在注释中写明未决编号和默认值的理由。

### 6. 新局与棋盘 `src/core/board.ts`

- 照 `01-board.md` 实现：
  - 坐标系和行优先遍历；
  - `InitNewGame` 的填盘顺序；
  - `RandomiseTile` 普通格的生成权重和条件变体；
  - 消除后的下落 `MoveMatchedTiles` 和补充；
  - 晋升计时的初始化。
- 敌人属性生成（`GenerateStats`）只实现普通骷髅的部分，特殊敌人的生成能力留给 T05。如果补充逻辑必须用到特殊敌人出现频率的判断，就按规格实现判断本身，具体是哪种特殊敌人可以先用占位。
- 补充和下落要能单独调用：测试里直接构造一个「标记了已消除格」的棋盘，再调用它们。

## 测试与可追溯

- 测试名前缀写规格出处，例如 `[01-board 普通格生成]`。如果 `07-test-cases.md` 里有对应编号，就写编号，例如 `C03`。
- 必须有的确定性测试：同一个种子 `NewGame` 两次，状态完全相同；不同种子得到不同的棋盘；连续调用补充时，RNG 调用的序列与规格描述的顺序一致。
- 新局要检查的不变量：36 格全部被填满；各类型的计数在合理范围内；第 0 路 COSMETIC 和第 1 路 TILE 的调用次数与规格一致。
