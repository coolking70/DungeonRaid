## 规则证据与设计

### 计分 / Pretzel

- `GetScore @0x2f868`：Classic 为 X+G+U+t+100L；Sprint 对每项分别 `trunc(/4)`，获胜再×2；Pretzel 只读累计交叉分。X/G/U 从 banked+remainder 取值，当前已花费金币不补回；技能分只看当前装备的技能，因此 Wish 移除后不再计分。
- `ProcessPretzels @0x2bcd8`：遍历全部链节点，包括箭头忽略节点；横/竖边不计，其余边用 `min(x)+6*min(y)` 作键，遇重复键加1。不使用通用线段交点算法，也不额外闭合首尾。
- k=0…4 得k，5…9得2k，10…14得3k，≥15得100；原生 `Game+15e34` 是0/1/2/3**评级档位**，并非交叉数。新增 `rating`，保留独立的派生 `crosses`。
- `MatchTiles @0x31bcc`：仅 Pretzel 有分链累加 score/count/max/avg；平均值每条链按整数除法截断。k>5排75，不限模式；Pretzel k≥15排77。三档计分标签39/40/41还按现有 cosmetics 模型消费 COSMETIC，不能因为没有绘制标签就省略抽样。
- 原生只证明**本链评级**，没有找到“整局评级公式”。结算提供 `bestChainRating`，明确表示以最大交叉数换算的最佳链档位，没有编造全局 S/A/B 等级。UI 可以显示档位/对应素材，不能将该字段解释为原版整局评级。
- `CheckEndGame @0x2f960` / `EndOfTurn @0x3289c`：保留第100回合尾部才成功的 Sprint 顺序；结束事件只发一次，附最终计分。

### 长期档案 / 榜单

- `CheckEndGame @0x2f960`：所有模式都给当前职业 games+1、kills+=局内直接击杀数；只有非挑战的 Normal/Hard/Harder 更新三个职业最高分。Easy 和挑战不更新这些最佳分。
- `ScoreScreen::AddScore @0x5cc5c`：分数降序，同分排在旧条目之后，最多10条。即使满榜且新分低于全部旧分，仍覆盖第10条；保留 `lastScoreIndices[category]`。原生+f24/+f28是一个全局类别/索引对，所以新增成绩会清掉其他类别的高亮（`SerialiseState @0x5cb34` 对其他类别写FF；`InitialisePage @0x5d0e0` 也检查类别）。
- 类别0…3为Classic四难度，4为Sprint，5为Pretzel。Sprint榜单的资源字段分别除4；Pretzel榜单 xp/gold/upgrade 三字段分别存 avgTimes10/maxCrosses/scoringChains，沿用原展示语义。
- `CharacterClass::LevelUp @0x3600c` 调 `UnlockAchievement @0x35fb0`，因此职业成就请求接在**领取奖杯改变等级的那一刻**，不在每次结算时无条件补发所有旧里程碑。种族成就读 `classes.json.defaultRace`，不使用改选种族。
- `applyRunResult` 要求 phase=ended 且有 outcome；它是“一次完成一局”的事务，应只调用一次。它不会凭“同种子同分”去重游戏，因为同样的一局可以合法再玩。中途用 `consumeAchievements` 后必须持有其返回的清空队列状态，避免重复累计进度。

### 跨局奖杯间隔：已闭合

**原版确实跨局保留，并且跨进程单独持久化。**

1. `Game::Game @0x28c8c/@0x290fc` 将 `+0x14da0` 初始化为0；`InitNewGame @0x2d7a4` 清本局奖杯数 `+0x14da4`，没有清 `+0x14da0`。
2. `Game::NewGame @0x2de68` / `StartChallenge @0x2de10` 在同一个 Game 上调用 InitNewGame，不重建 Game。
3. `DungeonRaidSurfaceView.java:131–132` 从 SharedPreferences 的 `PREFS_TROPHY` 调 `SetTimeToTrophy` 恢复。
4. 同文件 `:394–396` 在 `HasTimeToTrophyChanged()` 时保存 `GetTimeToTrophy()`；`Game::SetTimeToTrophy @0x24500` 直接写 `+0x14da0`。

选项 `trophyInterval` 默认 `carry-across-runs`，理由是上述外层持久化证据，而不再是推测旧内存残留。另一值 `reset-each-run` 明确每局从0开始。`ProfileState.trophyRemaining` 保存此长期值；`prepareNewRun` 和 NewGame 按选项同步，本局 awarded 始终重置。

这关闭 T03 的“是否跨局沿用”问题；原版五路局内存档与外层奖杯间隔分别保存的证据也已补全。COSMETIC 种子本身仍不是原版 FF03 保存内容；新格式明确保存全部六路。

## 新存档格式

版本1顶层：

```json
{"format":"dungeon-raid-port","version":1,"kind":"run","state":{}}
```

`kind`只能为对应读取函数的 `run` 或 `profile`。`state`存完整状态；所有字段必需，未知字段拒绝，版本不兼容明确报错，不合并默认值或修补缺失数据。

- run：36格全部载荷/坐标/标志；选择次序与ignored；全部技能原生ID、等级、冷却、充能、active；装备完整20项向量和外观；资源banked/remainder/carry/bonus；菜单候选、选择次序和卷轴；pending ID、来源、法力槽和目标槽；moving；phase及resumePhase/menuResumePhase；current/next、combo、delayedLastStand、classLevels；全部计分字段及成就队列；六路uint32种子及调用序号；options和diagnostics。
- profile：10职业完整配置、等级、局数、击杀及三个最佳分；百分比成就；六类最多10条榜单、最后插入索引；playerName；长期trophyRemaining。
- 数值不得是NaN/Infinity；整数字段校验范围，RNG种子是uint32、calls是非负安全整数；收益carry/bonus保留有限小数。JSON本身会丢掉IEEE负零，因此只对负零使用 `{"$number":"-0"}` 标签，恢复后 `Object.is(value,-0)` 仍真。
- 校验棋盘固定槽坐标、装备槽和图标/名称表范围、职业/种族/技能枚举、属性向量长度、当前技能数和唯一ID、资源余数/整百累计、pending/menu唯一ID与nextEffectId、菜单选择引用、链selected/ignored引用、阶段续接及终局一致性。档案另校验职业索引、成绩排序和高亮位置（最多一个类别非null）、成就进度范围/禁用45。
- **保存不会调用UpdateStats、重抽候选或RNG、重播升级/奖励**。读入即是保存时完整状态；没有根据装备重算而改变待结算暂态。
- 序列化输出不含函数闭包。I1的`scrollNativeWord`和测试观察钩子是外部依赖；若使用 supplied-native-fixture，恢复后调用step时仍须传同一fixture。默认 reject-unresolved 继续拒绝没有证据的分支。
- `serializeRun`返回 `{ json, achievementQueue }`。json中的run与输入完全一致；额外队列只表示这次保存可能触发的72，由调用方送进档案消费。这样既满足原版“保存触发”的语义，也不让保存次数改变局内状态/RNG。检查的是当前装备，菜单中未购买的候选不视为玩家已拥有装备。
- `deserializeRun(json)`、`serializeProfile(profile)`、`deserializeProfile(json)`分别返回run/string/profile。不接受FF03、FF00–02或legacy字节。
- 任一不合法输入抛 `SaveValidationError`，带字段路径和原因；不静默降级或恢复新局。

## 给调试界面的接口

### 计分和局终显示

`getScore(state)`取当前分数；`scoreBreakdown(state)`取明细。`GameOver`保留旧字段，新增`settlement`，其中有mode/score/turn、原始resources、各项contributions、multiplier和Pretzel专用统计。Sprint应显示各资源截断后的贡献及胜利×2；不要先将资源相加再除4。

Pretzel输入中显示 `state.pretzel.crosses / preview / rating`；提交后读 `PretzelScored` 的本链points/rating、累计total和averageTimes10。榜单/结算显示 Avg=averageTimes10÷10、Max=maxCrosses、Total=scoringChains；分数另显示score。bestChainRating只表示最佳链，不是整体评分。

### 成就、职业与存读档

```ts
// 中途处理成就：采用两个返回状态，避免重复消费同一增量。
const drained = consumeAchievements(profile, state);
profile = drained.profile;
state = drained.state;
// drained.events: AchievementProgress { id, before, after, unlocked }

// 每次收到ClassLevelChanged可立即同步档案。
profile = applyClassLevelChanged(profile, event, state.difficulty);
// 同一等级事件重复应用无新增进度；不匹配的旧事件明确报错。

// 保存；真正的存储I/O由UI负责。
const saved = serializeRun(state);
profile = applyAchievementRequests(profile, state.difficulty, saved.achievementQueue).profile;
// 将 saved.json 和 serializeProfile(profile) 写到UI自己的持久化介质。
// 如需应用关闭前即时保存跨局间隔，同时令档案trophyRemaining等于state.trophies.remaining。

// 读档：不要再NewGame或重新生成菜单。
state = deserializeRun(runJson);
profile = deserializeProfile(profileJson);

// 局终一次结算：可以传已清成就队列的state，也可以把最后队列交给它处理。
profile = applyRunResult(profile, state);
// 持久化profile，同时移除/标记已结算的run；不要再次结算同一个完成局。

// 新局前同步（而非读取局内档案后覆盖它）。
state = prepareNewRun(profile, createRunState(options));
state = step(state, { type: 'NewGame', seed, classId, difficulty, mode }).state;
// 自定义配置通过NewGame.character传ClassConfiguration，不把Profile整块塞进character。
```

`ClassLevelChanged`和领取奖杯队列都包含同一直接完成里程碑，已完成通知会去重，不会多累计。若UI只在局终持久化，`applyRunResult`也会从classLevels同步实际职业等级；中途持久化建议事件到达就应用。

为避免崩溃后重复计一局，UI需要把“档案结算+活动run删除/已处理标记”作为一个存储事务。core不访问localStorage，不使用时间戳、UUID或隐藏去重集合。这个事务是调用方生命周期边界，不是原版FF03兼容逻辑。

## 发现的规格问题（仅在本报告记录）

1. **原state字段注释将15e34叫crosses不准确。** ProcessPretzels明确写0/1/2/3，表示本链评级；已在代码拆分rating与派生crosses，未改规格文档。
2. **成就65的简表少了特殊敌人在场条件。** `Teleport @0x2ffb4:41–43` 的 `GetSpecialEnemyCount()>0` 才排0x41/+1。代码沿用T06的有证据分支，新测试锁定有/无特殊两侧。
3. **成就56的“特殊敌人击杀”有奖杯转换细节。** MatchTiles在AttackSkull返回后读取目标+25c；若奖励转Trophy，`SetType @0x64ef8:22` 已清enemyType为0，因此该次不会排Sniper。正例设置未到奖杯间隔，负例验证当场转Trophy。没有把攻击前身份强行缓存进此成就；43相反，ProcessAttack明确在攻击前缓存Spiky身份。
4. **Pretzel整局评级没有已知公式。** 原生评级为本链档位；对UI明确给最佳链档位，不擅自按总分划整局评级。
5. **原版S11–S17的字节断言与P2“不复刻存档格式”不兼容。** 已按任务要求改写为语义往返；新增版本1保持宽字段与原先遗漏的中途状态，不能拿这些测试声称二进制兼容。
6. **无合法移动不是已有终局规则。** CheckEndGame证据只覆盖HP和Sprint胜利，先行机器人盘面不能据此猜出自动洗牌或失败规则；保留复现并交P6核验。
